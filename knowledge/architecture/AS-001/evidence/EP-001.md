# EP-001: Minimum evidence plan

## Purpose and boundaries

This plan identifies the least costly evidence packages that could support a defensible F-001 comparison. It does not select an architecture, change a hard obligation, or treat planned work as evidence. Estimates are planning estimates for the hypothetical target, not measured effort or timing. All gates require recorded artifact revisions and independent review; authors do not approve their own evidence.

AE-001 leaves C-002 and R-001 unresolved for both candidates, and AP-001's R-002/R-003 unresolved. AP-002's abstract exactness and mathematical range are established by PR-002 under its stated integer and abstract-ring assumptions; the C mapping, state correspondence, synchronization, memory and target performance remain open.[^evaluation][^review] F-001 requires all hard obligations before comparing state SRAM, worst-case cycles per update, and flash bytes.[^merit]

## Shared evidence and stopping rule

Packages 1 and 3 should use the same target ABI, detector budget definition, compiler configuration, harness, and reporting template for both candidates. Package 2 reuses PR-002 for AP-002's abstract mathematics but not for implementation correctness; AP-001 requires its own proof. Run packages 1 and 2 before expensive target timing. If a candidate fails an accepted hard requirement, stop its downselection campaign and revisit the smallest applicable design decision; do not lower the requirement. Preserve separate candidate results and source revisions even when methods are shared.

## Claim classes and gates

- **Mathematical guarantee:** PR-002's reviewed bounds and recurrence apply over its stated integer domain and abstract ring contract. A new AP-001 proof can establish corresponding universal facts for recomputation. Neither result implies a C expression or target implementation is safe.[^review]
- **Static implementation claim:** type promotion, source-to-proof correspondence, object layout, linker map and stack analysis depend on concrete declarations, compiler ABI, build options, and system scope.
- **Target-specific claim:** WCET/cycle behavior and any runtime margin depend on the target, clock, compiler output, interrupts, and workload. They require the controlled target campaign; synthetic data cannot establish them.[^evaluation]
- **Gate 1 — AP evidence ready:** packages 1 and 2 independently reviewed, with any later implementation-only work explicitly tracked under VO-002/004/005/006. This is not itself a candidate PASS if a hard obligation remains unresolved.
- **Gate 2 — target validation ready:** package 3 accepted for each still-feasible candidate; no deadline or planned measurement counts as PASS.
- **Gate 3 — ranking ready:** every C/R obligation accepted for candidates under comparison; then apply F-001 unchanged and, only if needed, obtain the documented stakeholder trade-off. No architecture is selected by EP-001.

## Known limits

No target measurements, implementation source, compiler output, or concrete memory layout was inspected or created for this plan. The synthetic evidence fixture is not used as proof or target performance evidence. Costs are rough person-day ranges and must be revised if hardware/tool access or implementation scope differs.[^evaluation]
