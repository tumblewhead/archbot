# PR-002: Independent acceptance review of PE-001-v2

## Disposition: ACCEPT_WITH_CLARIFICATIONS

PE-001-v2 establishes the stated mathematical claims over integers and an abstract 32-slot ring under its explicit domain, initialization, and update assumptions. It resolves both material PR-001 findings: the add-before-subtract transient is bounded by `33 * 4095^2`, and C multiplication safety is conditioned on the actual promoted operand type or widening before multiplication. This disposition accepts the proof package's abstract mathematics; it does not establish that a C implementation meets those conditions, approve AP-002, or approve firmware.[^proof][^prior_review][^statement]

The phrase “mathematical accumulator value fits in a signed 32-bit integer” is a range observation only. It must not be read as a claim about C expression evaluation or a concrete implementation. Likewise, the ring invariant is conditional on the oldest-slot and update-order conventions being implemented exactly.[^proof]

## Independent checks

### Universal squared-sum bound

For each of the 32 window elements, `0 <= w_j <= 4095`, so `0 <= w_j^2 <= 4095^2 = 16,769,025`. Therefore

`0 <= S_t <= 32 * 16,769,025 = 536,608,800 < 2^29 = 536,870,912`.

The upper bound is attained when all 32 samples are 4095. This verifies the universal bound for every legal sequence, including zero-padded startup, and establishes representability of the mathematical value in 32-bit signed and unsigned integer ranges.[^statement][^adc][^opportunity]

### Exact recurrence, startup, and modulo-32 wraparound

Before an update, assume the slots in age order represent the preceding 32 values, with missing history zero, and `A` is their sum of squares. The indexed oldest slot contributes `o^2` to `A`, so `A-o^2 >= 0`. Replacing it with `x` gives the next window exactly, and its sum is `A-o^2+x^2`. This is an induction invariant, not merely an equality of aggregate values: it depends on the slot order and the index designating the oldest member.

The all-zero initial ring and accumulator establish the base case. During the first 31 updates, indexed zero slots encode the absent prehistory; no special arithmetic rule is needed. Advancing the index once modulo 32 after replacement restores the oldest-slot convention, including the transition from index 31 to 0. The argument then repeats on every wrap. PE-001-v2 states these preconditions and proves the transition; they agree with AS-001's zero-padded startup requirement.[^proof][^statement][^opportunity]

### Add-before-subtract intermediate

From any valid window, `A <= 32*M^2` and `x^2 <= M^2`. Thus the transient under add-before-subtract is at most `33*M^2 = 553,377,825`. This is below `2^31` and `2^32`; the final value after removing the oldest square is the next window sum and returns to the universal bound. PR-001's contrary claim that this transient could exceed `2^32` is corrected. The bound relies on starting from a valid window and one incoming sample; it does not cover arbitrary corrupted state or multiple unbounded additions.[^proof][^prior_review]

### C integer promotions and portability

PE-001-v2 correctly distinguishes mathematical bounds from C expression types. If a `uint16_t` operand promotes to a 32-bit `int`, the maximum product fits in that `int`. On an implementation where the operands instead promote to 16-bit `unsigned int`, multiplication can wrap at 16 bits before a wider assignment; `4095u * 4095u` then yields 64513 modulo 65536. Widening operands to a suitable 32-bit type before multiplication, or establishing that the promoted type holds the full product, addresses that issue. The conversion must precede multiplication; assignment to a wide accumulator after a narrow product is insufficient.[^proof][^prior_review]

The package appropriately leaves concrete conclusions conditional on inspecting declarations, available exact-width types, integer widths and ranges, language mode, expression forms, and range validation. The synthetic Cortex-M-class assumption does not determine those compiler properties.[^target][^proof]

## Resolution of PR-001 findings

- **Add-before-subtract overflow counterexample:** resolved. The corrected bound is `553,377,825`, below both signed and unsigned 32-bit maxima for the one-update transient from a valid state.[^proof][^prior_review]
- **Overbroad unsigned-promotion safety claim:** resolved. PE-001-v2 explains narrow unsigned multiplication and requires widening before multiplication or a concrete promotion-width argument.[^proof][^prior_review]
- **Implementation evidence absent:** remains open as an implementation obligation, not a defect in the abstract proof. No C source, compiler configuration, or generated code was available in this review.[^proof][^target]

## Established claims and remaining obligations

**Established mathematically, under the stated integer domain and abstract ring contract:**

1. For every legal sequence and every `t >= 0`, `0 <= S_t <= 536,608,800`, with a tight upper bound.
2. The exact rolling-window recurrence and accumulator invariant.
3. Zero-padded initialization and the first 31 updates.
4. Correct eviction and invariant preservation through every modulo-32 wrap, when the index names the oldest slot and advances once after replacement.
5. Subtract-before-add intermediates are in `[0, 32*M^2]`.
6. Add-before-subtract transient from a valid state is at most `33*M^2 = 553,377,825`; it does not overflow a mathematical 32-bit signed or unsigned value.

**Still requiring implementation evidence:** actual declarations, integer promotions and expression widths; availability and use of `uint32_t`; input range enforcement before squaring; accumulator type and update order; initialization and reset consistency; oldest-slot/index sequencing; synchronization against partial updates; generated code; WCET; memory use; and overall firmware correctness. No implementation obligation is discharged by this review.[^proof][^target][^statement]

## Suggested next gate

Use PE-001-v2 as the accepted mathematical basis for a later contract or implementation review. Check the concrete C expression types, range checks, state transitions, initialization, and concurrency against the listed obligations. This review does not approve AP-002 or firmware.[^proof][^statement]
