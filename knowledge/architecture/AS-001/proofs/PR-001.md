# PR-001: Independent proof review of PE-001-v1

## Disposition: REVISE

The universal mathematical bound and abstract rolling-window invariant are valid under the stated sample-domain, initialization, and ring-order assumptions. The proof package has material errors in its overflow analysis for add-before-subtract and in its discussion of integer promotions on implementations with a 16-bit `unsigned int`. Correct those claims before treating the C arithmetic discussion as reliable. This review does not approve AP-002 or any firmware implementation.

## Independent derivation of the accumulator bound

Let each window element be an integer `w_j` with `0 <= w_j <= 4095`. Since squaring is monotone on nonnegative integers,

`0 <= sum(j=0..31, w_j^2) <= 32 * 4095^2`.

`4095^2 = 16,769,025`; hence `32 * 16,769,025 = 536,608,800`. Also `2^29 = 536,870,912`, so the maximum is strictly below `2^29`, and thus below both signed and unsigned 32-bit maxima. The bound is attained by a full window of 32 samples all equal to 4095. This independently establishes PE-001-v1 Theorem 1 and the universal accumulator value bound in PO-001.[^proof][^opportunity][^statement]

## Independent invariant and boundary analysis

Use the invariant that, before accepting the next sample, the 32 logical slots contain the preceding 32 samples in age order, with absent prehistory represented by zero, and `A` equals the sum of their squares. Let `o` be the oldest slot and `x` the incoming sample. The next logical window removes `o` and includes `x`, so its sum is exactly `A - o^2 + x^2`. Since `o^2` is one nonnegative term in `A`, `A >= o^2` and subtraction is nonnegative. The resulting mathematical value is the next window sum and so obeys the same universal bound.

At startup, initialize all slots and `A` to zero and point the write index at any slot designated oldest. Each of the first 31 updates removes a still-zero prehistory slot and inserts one real sample; the invariant follows directly. At the 32nd and later updates, the oldest value is the sample leaving the finite window. Replacing the indexed oldest slot and advancing modulo 32 restores the age-order convention, including the transition from index 31 to 0. The argument does not depend on the numeric index, only that it identifies the oldest slot and advances exactly once after replacement. Thus the mathematical invariant is valid; the implementation must still realize these exact conventions.[^proof][^opportunity]

## Overflow claim: add-before-subtract

PE-001-v1 states that from a full window of 32 maximal samples, adding one maximal square before eviction "would exceed 2^32" and can wrap a 32-bit accumulator. This is false. The transient sum is

`33 * 4095^2 = 553,377,825`,

which is greater than `2^29 = 536,870,912` but far below `2^31 = 2,147,483,648` and `2^32 = 4,294,967,296`. Therefore that specific transient neither overflows a 32-bit signed integer nor a 32-bit unsigned integer. More generally, starting from any valid window, one add-before-subtract intermediate is at most `32*M^2 + M^2 = 33*M^2 = 553,377,825`, so it is still safe at 32 bits. The final recurrence remains exact if the addition and subtraction are done with sufficiently wide, correctly evaluated operands. The claim that add-before-subtract can wrap a 32-bit accumulator is unsupported and refuted by the universal bound; a 16-bit accumulator or a different state bound would be a separate matter.[^proof][^opportunity]

Subtract-before-add is sound mathematically: intermediate `A-o^2` lies in `[0,A]` and the post-add result is the next bounded window sum. This establishes ordered-update safety for a mathematical 32-bit value. It does not by itself establish safe C evaluation for every possible operand type.

## C integer promotions and unsigned arithmetic

The conditional analysis for a 32-bit `int` and 16-bit sample values is sound: the samples promote to `int` where representable, and the maximum product 16,769,025 fits a signed 32-bit `int`. The `uint32_t` compound assignment then converts that product to the accumulator's unsigned type; because it is nonnegative and below `2^32`, conversion is exact. With the invariant, unsigned subtraction cannot underflow.

However, PE-001-v1 further says that even if `uint16_t` promotes to `unsigned int` instead of `int`, the maximum product remains representable in 32-bit unsigned arithmetic. This omits the width of the type in which multiplication actually occurs. On a conforming implementation with 16-bit `int` and 16-bit `unsigned int`, 16-bit unsigned operands can multiply in 16-bit `unsigned int` and wrap before compound assignment widens the result to `uint32_t`. For example, `4095u * 4095u` modulo 65536 is 64513, not 16,769,025. A declaration using `uint16_t` alone therefore does not ensure a wide product. The implementation must widen operands before multiplication (for example, cast to `uint32_t` before multiplying) or establish that the promoted operand type can represent the full product. This review does not assert that the hypothetical Cortex-M target uses 16-bit `int`; the proof package's generic C claim is simply too broad.[^proof][^statement]

Additionally, the review's assumptions that `uint32_t` and `uint16_t` exist and have specified widths do not alone establish the width of `int`, `unsigned int`, the promoted sample type, or actual expression type. The language version, declarations, range validation before multiplication, and expression form must be checked in the concrete implementation. The mathematical accumulator bound remains independent of these C-specific obligations.[^proof]

## Claims separated by evidence class

- **Established mathematically:** `0 <= S <= 536,608,800`; zero-padded startup; exact abstract recurrence; nonnegative subtract-before-add intermediate; modulo-32 ring invariant, assuming the index designates the oldest slot and updates in the specified order.
- **Refuted:** the claim that add-before-subtract from a valid 32-sample state can overflow 32-bit arithmetic for this domain; the stated transient is at most 553,377,825.
- **Unsupported as written:** generic C multiplication safety for 16-bit samples when promotions produce a 16-bit unsigned type. Widening before multiplication or a concrete implementation argument is required.
- **Uninspected implementation obligations:** actual declarations and compiler/language settings; range enforcement; initialization/reset paths; index sequencing; concurrency/atomicity; generated code; WCET and memory layout. No implementation or compiler output was reviewed.

## Suggested next gate

Revise PE-001-v1's C arithmetic paragraph and remove or correct its add-before-subtract overflow counterexample. Then conduct a separate implementation review against actual declarations and compiler settings. Do not add a `proven_by` relation on the basis of this review alone; this disposition identifies revisions needed in the proof package's implementation-specific claims.[^statement]
