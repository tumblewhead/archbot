# PE-001 v2: Corrected rolling-sum proof package

## Scope and assumptions

This package proves claims about mathematical integers and an abstract ring-buffer state. It separately lists conditions for mapping those claims to C. It does not inspect firmware, select an architecture, approve AP-002, or establish target timing. Let the sample domain be the integers `[0,M]`, where `M=4095`, and let the window length be `N=32`, as declared by AS-001 and the ADC assumption.[^as][^adc]

At time `t >= 0`, define `w_(t,j) = x_(t-j)` when `t-j >= 0`, and `0` otherwise, for `j=0,...,31`. Define `S_t = sum(j=0..31, w_(t,j)^2)`. Before accepting a sample, the abstract ring contains the preceding window in age order, with absent prehistory as zero, and accumulator `A` equals that window's sum. An update removes the oldest value `o`, inserts incoming value `x`, and advances the write index exactly once modulo 32.

## Theorem 1: universal accumulator bound

For every legal sequence and every `t >= 0`,

`0 <= S_t <= 32 * 4095^2 = 536,608,800 < 2^29 < 2^32`.

**Proof.** Every window element is an integer from 0 through 4095, so its square is in `[0,4095^2]`. Summing 32 such bounds gives the result. Since `4095^2 = (4096-1)^2 = 16,769,025`, multiplication by 32 gives `536,608,800`. This is strictly less than `2^29 = 536,870,912`. The bound is attained by 32 maximal samples. Thus the mathematical accumulator value fits in 32 unsigned bits (and also in a signed 32-bit integer); this representability statement alone says nothing about the type used to evaluate an intermediate C expression.[^as][^adc]

## Theorem 2: exact rolling invariant, startup, and wraparound

If all ring slots and `A` start at zero, the index identifies the oldest slot, and each update subtracts that slot's square, replaces it by the incoming sample, adds the incoming square, then advances the index modulo 32, the ring represents the zero-padded logical window and `A` equals its exact square sum after every update.

**Proof.** Initially the 32 zero slots encode the empty history with zero padding, and their sum is zero. Assume before an update that the slots are exactly the preceding 32 logical window values and `A` is their sum of squares. Since `o^2` is one nonnegative term of `A`, `A-o^2 >= 0`. Removing `o` and inserting `x` gives precisely the next logical window, so its sum is `A-o^2+x^2`; this proves the induction step. In the first 31 updates, zero-initialized slots supply the missing prehistory, so the same argument applies without a separate arithmetic rule. At and after the 32nd input, the outgoing value is the oldest real sample in the finite window. Replacing the indexed oldest slot then advancing the index modulo 32 restores the age-order convention. The proof applies equally when index 31 advances to 0, and at every subsequent wrap. By Theorem 1 the post-update value is at most `536,608,800`.[^as][^adc][^po]

## Exact intermediate bounds and update order

For subtract-before-add, `0 <= A-o^2 <= A <= 32*M^2`. After adding `x^2`, the result is the next window sum and is at most `32*M^2`.

For add-before-subtract, starting from a valid window, the transient is `A+x^2`, hence

`0 <= A+x^2 <= 32*M^2 + M^2 = 33*M^2 = 553,377,825`.

This bound is attained when the current window and incoming sample are all maximal. The transient is above `2^29`, but below `2^31 = 2,147,483,648` and `2^32 = 4,294,967,296`. Therefore the v1 claim that this case exceeds `2^32` and can overflow a 32-bit accumulator was incorrect; add-before-subtract does not overflow a mathematical 32-bit signed or unsigned value for this one-update bound. The final value after subtracting `o^2` is again the next window sum. These mathematical bounds do not guarantee C expression safety when squaring or adding in narrower or otherwise unsuitable types.[^review][^v1]

## C mapping conditions (implementation-specific obligations)

The abstract theorems do not establish the actual C expression types. Integer promotions apply to each operand before multiplication. If a `uint16_t` sample promotes to a 32-bit `int`, values through 4095 and their product through 16,769,025 are representable, so that product can be evaluated exactly in `int`. But if the operands promote to a 16-bit `unsigned int`, multiplication occurs at that width and may wrap before assignment to a 32-bit accumulator; for example, `4095u * 4095u` modulo 65536 is 64513. A later widening assignment cannot recover the lost value. The v1 assertion that the unsigned-promotion case is safe merely because the desired product fits a 32-bit unsigned type was therefore too broad.[^review]

The implementation must widen operands **before multiplication**, such as by converting each operand to `uint32_t` before multiplying, unless the concrete target's arithmetic rules establish that the promoted operand type can represent the complete product. The actual declared types, integer widths/ranges, language version, and expression forms must be inspected. The sample range must be enforced before multiplication; casts do not validate input. Also verify accumulator updates use a type and order that preserve the established bounds, startup/reset initializes the array and accumulator consistently, the index identifies the outgoing slot and advances exactly once modulo 32, and concurrency does not expose a partially updated state. The assumed Cortex-M class does not itself establish compiler settings or all these facts.[^as][^target][^review]

## Claim classes and outstanding obligations

**Mathematically established under the stated domain and abstract update contract:** (1) `0 <= S_t <= 536,608,800`, tight; (2) exact recurrence and invariant; (3) zero-padded startup and first-31-update behavior; (4) correct eviction through modulo-32 wraparound; (5) subtract-before-add intermediates lie in `[0,32*M^2]`; and (6) add-before-subtract transient is at most `33*M^2 = 553,377,825`, not a 32-bit overflow counterexample.

**Not established without implementation evidence:** actual integer promotions and multiplication width; presence and behavior of `uint32_t` on the compiler; pre-square range validation; concrete update/index ordering; initialization and reset paths; synchronization/atomicity; generated code; WCET; memory use; and full firmware correctness. No implementation or compiler output was inspected.[^review][^target]

These claims are submitted for independent acceptance as a corrected proof package. This artifact does not independently review or approve itself. It does not choose an architectural proposal or approve firmware.[^review]
